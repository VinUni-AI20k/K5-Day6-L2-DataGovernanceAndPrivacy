# T08 · Retention & Delete Request Simulator

**Độ khó:** CPU · dễ · **Topic Day06:** E3, H2, E2 · **Fixture:** `fixtures/t08_deletion/` · **Config:** `configs/tracks/t08.yaml`

> Xử lý 10 yêu cầu xóa: truy lineage (raw → frame → crop → embedding, backup, export), tôn trọng legal hold/ngoại lệ, dry-run, audit.

**5 bước bắt buộc:** Nhận delete request → Truy ngược lineage → Dry-run & exception → Human approve exceptions → Delete mock + evidence

## 1. Dữ liệu có sẵn (offline)

| File | Nội dung |
|---|---|
| `data_graph.json` | 212 artefact mock: `type, subject_ids, parent_ids, uri, owner, acl, legal_hold, origin_known`. |
| `requests.json` | 10 yêu cầu xóa (`subject_id`, deadline). |
| `gt/gt_actions.csv` | `expected_action ∈ {delete, retain_legal_hold, escalate}` cho từng (request, artefact) — chỉ evaluate. |

`manifest.csv` (input) và `gt/manifest.csv` (ground truth) chứa `source, license, split, sha256` — pipeline kiểm hash ở bước load.
**Pipeline không được đọc `gt/`** (GT guard trong `src.main` sẽ dừng với exit code 5).

**Dữ liệu thật (tuỳ chọn, nếu giảng viên đã chuẩn bị `data/real/`):** Không dùng dữ liệu thật — **không xóa dữ liệu thực trong lab**.

## 2. Output contract

`out/actions.csv`: `request_id, artefact_id, action ∈ {delete, retain_legal_hold, escalate}`. Ghi `out/audit_log.jsonl` (`ctx.audit`) để được chấm audit completeness.

`src.main` kiểm tra file và cột bắt buộc; thiếu → exit code 2.

## 3. Metric (đã cài sẵn trong `src/metrics/tracks.py::eval_t08`)

- **Primary — Deletion Completeness** = artefact phải xóa đã xóa / toàn bộ artefact phải xóa.
- Secondary: **False-delete count (mục tiêu 0)**, exception handling accuracy, audit trace completeness, latency.


## 4. Baseline (nhóm tự cài) + thí nghiệm công bằng

- **Baseline:** Xóa một bản raw theo filename, không tìm derived/backup.
- **Protocol:** Có case legal hold + case thiếu quyền/unknown origin + artefact nhiều subject. Idempotency: chạy 2 lần phải ra cùng kết quả.
- Cùng pool / budget / seed 42 / heldout cho baseline và PoC. Báo cả kết quả bằng 0 hoặc âm.

## 5. Failure mode bắt buộc phải phân tích

Xóa nhầm dữ liệu thuộc exception; chỉ xóa raw nhưng giữ bản sao và embedding định danh.

Fixture đã cài sẵn một số case cho các failure mode này — nhóm phải tự tìm, minh hoạ bằng ảnh/metadata và nêu root cause.

## 6. Human review + quyết định

Bảng request → artefact → exception → người duyệt → hành động & log.
Dùng `src/common/review.py` (queue, overrides, `AuditLog`), `src/common/contact_sheet.py` (HTML offline có nút Export CSV) và `src/common/decision.py` (GO/HOLD/REWORK + `reason_code` + `owner`).

## 8. Gợi ý hướng nghiên cứu (không phải đáp án)

Graph traversal (BFS qua parent/children); policy precedence: legal hold > permission > multi-subject > delete; dry-run diff.

Ví dụ cần phân tích: **legal hold vs quyền xóa** — yêu cầu xóa không được thực hiện ngay khi dữ liệu đang bị giữ theo nghĩa vụ pháp lý (Luật 91/2025 có các ngoại lệ đối với quyền xóa; GDPR Đ.17(3)). Quyết định phải ghi `reason_code` + căn cứ và hẹn xóa khi hết hold. So sánh: California **DROP** (Delete Request and Opt-out Platform) cho phép một yêu cầu xóa gửi tới mọi data broker đã đăng ký.
